# RViz 目标点发布后车辆不动的诊断与修复

这次记录的直接阻断点在规划适配层的数据新鲜度判断。RViz 的三个目标点都被收到，但规划端一直输出空参考，跟踪端下发的所有速度都为零。已添加读取现有 map → odom → body TF 的适配方式，定位算法、定位话题发布和 TF 发布保持原样。修复已通过离线检查，尚未在车机 ROS 2 Humble 或实车上验证。

## 实际证据

数据来源为 `record_data/run_19700109_151544_181276302`，包含两个原始 SQLite bag 分片。`evidence.json` 给出完整统计，`analyze_recording.py` 可只读重算。

| 环节 | 本次记录 | 含义 |
| --- | --- | --- |
| RViz 目标 | 3 次，约在录制后 51.75、57.87、63.79 秒 | 目标已收到，话题链路接通 |
| /localization | 3121 条，约 43.08 Hz；只有 187 个不同源时间戳 | 到达频率不能代表源时间戳更新频率 |
| /localization 源年龄 | 中位数 1.483 秒，最大 2.671 秒 | 超出感知 0.5 秒门限 |
| 同源时间戳的内容 | 21 组消息的位置发生变化 | 当前直接去重还会漏掉这些位置更新 |
| 感知检查 | 1325 次 localization_stale，1 次 published | 99.92% 的点云未进入正常障碍物发布流程 |
| /rda/obstacles | JSONL 和原始 bag 均只有 1 条 | 障碍物超时并非记录器漏收造成 |
| 目标后的规划诊断 | localization_fault 190；obstacle_timeout 103；planning_pending 2；planning_budget 1 | 尚未形成可跟踪路径 |
| /rda/plan | 686 条，非空 reference 为 0 | empty_plan 是上游阻断的结果 |
| /car_cmd | JSONL 3445 条，非零速度为 0 | 车辆接收到的意图就是停车 |
| 写入健康 | dropped=0，write_errors=0 | 结构化日志没有记录到写入丢失 |

原始 bag 的 /car_cmd 数量为 3437，与逐消息记录的 3445 有边界/接收差异；上述 JSONL 和 bag 的计数分别保留在证据中，没有把两者混为同一数据流。

定位位姿的正确性与消息时间戳语义是不同问题。这些记录支持适配层误用旧融合时间戳的判断，不需要修改定位算法内部实现。原始 bag 的当前 TF 源年龄为：map → odom 中位数约 1.38 ms，odom → body 中位数约 21.31 ms。

底盘诊断中 run_enable=true，并曾收到 enable=255、ctrmode=1 的回显；发送日志中可以看到零速 Car Run。这说明本次不应先把 run_enable 当作根因。底盘后来没有持续状态回包，因此这些记录也不能单独证明整个底盘反馈链路正常。

终端构建输出的 Clock skew 警告与车机当时的 1970 年系统日期一致；7 个包都完成了构建。建议另行校正车机时间，但这不足以解释已明确记录的数据过期和零速链路。

## 修改内容

生产补丁共六个文件，路径都相对工作空间根目录：

- `src/rda_dwa_real/rda_dwa_real/localization_input.py`：新增现有 TF 的只读适配器。
- `src/rda_dwa_real/rda_dwa_real/lidar_track_node.py`：感知前从 TF 获取当前 body 位姿。
- `src/rda_dwa_real/rda_dwa_real/bridge_node.py`：规划前从同一 TF 链获取位姿。
- `src/rda_dwa_real/rda_dwa_real/traj_tracker_node.py`：控制前从同一 TF 链获取位姿。
- `src/rda_dwa_real/config/real_vehicle.yaml`：三个节点统一配置 `localization_source: tf`，父帧 map，子帧 body。
- `src/rda_dwa_real/package.xml`：声明 tf2_ros 运行依赖及测试 YAML 依赖。

TF 查找采用最新共同时间，控制回调不等待 TF。仍按 TF 的源时间戳检查新鲜度；重复源时间戳不能延长核心定位看门狗。TF 失效时不自动使用旧 /localization 数据。现有 0.35/0.5 秒门限、车辆尺寸、body_to_base_link_x=0.0、规划算法与底盘代码均保持原配置。topic 模式作为显式回滚选择保留。

使用 ROS 官方 TF2 监听 API，参考 [ROS 2 Humble Python TF2 listener](https://docs.ros.org/en/humble/Tutorials/Intermediate/Tf2/Writing-A-Tf2-Listener-Py.html)。

## 离线验证

1. 源码与录制 provenance：修改前核对的 12 个 Python/配置文件 SHA256 均匹配本地源码。五个被修改的旧文件已存放在 `before/`，原哈希见 `before_sha256.json`。
2. 原始 TF 数学回放：在共同源时间进行完整 3D 变换组合与插值，1326/1326 个感知检查满足 0.5 秒门限；3442/3443 个控制检查满足 0.35 秒门限。余下 1 个控制检查仍应触发停车。此结果为离线近似，不能代替真实 tf2 缓存、DDS 调度与网络延时测试。
3. 核心位姿回放：1121 个新源样本；目标发布后未发现触发当前位姿跳变守卫的样本。初始定位阶段有一次约 0.325 m 的地图位姿修正，发生在第一个目标之前；单独记录了由它触发的初始停车检查，未删除跳变守卫。见 `core_tf_replay.json`。
4. 六个回归测试通过：最新 TF 帧和源时间；无 TF、过期、未来与无效数值拒绝；topic 兼容模式；重复源 TF 不续期；三个节点拒绝旧话题覆盖；前方目标生成非空参考和非零速度，随后 TF 断流将速度归零。采用 ROS 替身，未发送 DDS 或 UDP。日志见 `unit_tests.log`。
5. 修改过的 Python 文件通过语法编译检查。

目前未完成车机 colcon 构建、真实 ROS 2 Humble TF2 行为验证、完整点云避障闭环回放或实车行驶验证。当前回放验证的是定位适配和时间门限，不能据此声称实际道路场景已经能安全通过。

## 部署和复测

先结束旧的 launch，将补丁 zip 拷到车机现用工作空间根目录。原始定位包不需要替换。以下路径与本次终端日志一致：

```bash
cd ~/Desktop/Wxk/car_gpt
unzip -o hotfix_rviz_tf_20261107.zip -d .
colcon build --symlink-install --packages-select rda_dwa_real
source install/setup.bash
ros2 launch car_launch run_rda_dwa.launch.py
```

按原流程在 RViz 完成定位，然后发布目标。用另一终端 source 同一个工作空间后检查：

```bash
ros2 param get /lidar_track_node localization_source
ros2 param get /rda_dwa_real_bridge localization_source
ros2 param get /traj_tracker_node localization_source
ros2 run tf2_ros tf2_echo map body
```

三个参数应为 tf；TF 应持续更新。再看感知和规划诊断：

```bash
ros2 topic hz /rda/obstacles
ros2 topic echo /rda/perception_diag --once
ros2 topic echo /rda/diag --once
ros2 topic echo /rda/control_diag --once
ros2 topic echo /car_cmd --once
```

重点看 `localization_input.reason=tf_valid`、源年龄、感知 reason、规划 reason 与 reference，而不是仅看话题是否有发布。开阔场地中，前方未到达目标的正常可行规划应有非空参考，并最终出现正速度；遇到障碍或输入异常仍可保持停车。

## 第二个待验证问题

录制后约 79.40 秒的唯一已完成计算耗时 0.135835 秒，超过 `planning_budget_s=0.08`，被标为 planning_budget 并丢弃。该次计算时只有 1 帧感知恢复，所以当前证据不足以断言所有正常感知后的规划都会超时。

本补丁没有放宽计算预算或安全检查。时间适配恢复后，若仍反复出现 planning_budget，下一步要在车机测 worker_duration_s、result_age_s、障碍数量及点云处理耗时，针对热点优化并重新验证参考有效期。若为 blocked 或 dynamic_yield，则应按现场障碍数据分析其可行性，不能通过强制非零速度绕过。
