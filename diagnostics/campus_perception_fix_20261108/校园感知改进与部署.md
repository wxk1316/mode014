本次已修改当前工作区的雷达检测代码，针对学校无车道线、道路与不可行驶区域约有 10 cm 高差的环境。修改日期为 2026-11-08；运行入口仍是 `ros2 launch car_launch run_rda_dwa.launch.py`。

生产改动仅有三个文件：

- `src/rda_dwa_real/rda_dwa_real/perception_core.py`：道路平面、上下台阶保留、精确连通性回查、父簇支持保留、局部空腔表达和观测栅格。
- `src/rda_dwa_real/rda_dwa_real/lidar_track_node.py`：新参数接入；同步和异步发布观测栅格；保留原始点云时间戳。
- `src/rda_dwa_real/config/real_vehicle.yaml`：校园道路参数。

现有检测与跟踪消息接口保持兼容。新增的 `nav_msgs/msg/OccupancyGrid` 来自项目原本已依赖的 `nav_msgs`，数值计算仍只需要 NumPy；没有增加 SciPy 或学习模型依赖。

四个审查问题的处理如下：

| 原问题 | 当前处理 | 同一合成输入的结果 |
| --- | --- | --- |
| 体素极值遗漏唯一连通边 | 极值快速检查不能确定时，按原始 XY 点回查；仅使用小块距离数组，并限制总计算量 | 10 点原始连通簇从漏检恢复为 1 个检测，全部点被包围 |
| 长结构分块后全被过滤 | 在父簇筛选可靠性，子块保留父簇全部观测支持，不再逐块执行父簇的最少点数规则 | 4 m / 16 点结构输出 5 块，端点也保留 |
| 低平台顶面变成地面 | 空间平衡采样、受参考高度约束的平面假设、近车道路支持加权及跳变/覆盖校核 | 30 cm 密集平台在有/无既有地面先验时均保留 |
| 小 U/L 形被整框填满 | 按包围框空占据率及车体相交条件触发局部分块；车旁采用 0.4 m 网格，远处采用 1.2 m 结构网格控制对象数量 | 2×2 m U 形输出 16 个局部框，全部墙点保留，整个 1.2×0.8 m 车体位于空腔 |

计算预算耗尽时返回 `valid=False`，不把不完整连通图当成合法空场景。地面估计失败只允许短时间使用既有地面，超过复用时限后停止刷新检测和观测栅格。

校园道路使用以下默认值：

| 参数 | 值与含义 |
| --- | --- |
| `obstacle_height_min` | 0.06 m，保留高于道路 6 cm 的回波，覆盖约 10 cm 路沿 |
| `dropoff_height` | 0.06 m，保留低于道路 6 cm 的可观测回波，覆盖向下台阶 |
| `boundary_min_points` / `boundary_min_extent` | 3 点 / 0.30 m，保留有连续长边支持的稀疏低边界；普通三点高回波仍走原噪声筛选 |
| `boundary_max_height` | 0.20 m，上述稀疏边界规则只用于低矮高差 |
| `ground_reference_z` | -0.36 m，base_link 原点处的道路高度，取自现有录制；它不是雷达安装高度 |
| `ground_reference_tolerance` | 0.05 m，拒绝将相差约 10 cm 的平行外部区域当作车所在道路 |
| `drivable_max_height` | 0.035 m，观测道路支持的高度容差 |
| `drivable_resolution` | 0.20 m，观测栅格分辨率 |
| `max_distance_tests` | 2,000,000，精确连接回查的距离测试预算 |

**安装高度或 base_link 参考发生变化后，应先校核 `ground_reference_z`。** 当前值来自录制平面约 -0.36 m；不能把 `lidar_height=0.45` 直接填入这个参数。参数不匹配时算法会拒绝地面估计，诊断中的 `ground_fit_reason` 会说明原因。

道路边界及观测到的高/低外部表面通过原有 `/rda/obstacles` 进入避障输入。新增 `/rda/drivable_area` 用于查看和后续接入道路约束：

- `header.frame_id=base_link`，时间戳为原始点云采集时间，分辨率 0.20 m。
- `0`：该格有足够的道路高度回波支持。
- `100`：该格观察到凸起、向下台阶或障碍回波；优先于同格道路回波。
- `-1`：未知，包括没有回波、遮挡、被车体自过滤及高度证据不足的格子。

栅格不做射线清空、空洞填充或越过边界的道路外推。`0` 表示表面证据，不表示整车足迹已经有足够净空。现有规划器仍消费 `/rda/obstacles`，本次没有增加规划器对新栅格的订阅，所以不应把新栅格的发布等同于规划器已经实施了“未知区域禁止进入”的硬约束。未观测到的台阶不能凭空检测，植被、严重多层路面及非平面道路仍需要有真值的实录验证。

验证结果已保存在 `validation.json`、`raw_comparison.json` 和 `test_summary.json`：

- 活动测试 `src/rda_dwa_real/test`：107 passed、1 xfailed、10 subtests passed。本次新增 21 个测试，覆盖原始点图等价性、点顺序和等坐标、预算失效、完整端点包络、U/L 空腔、密集平台、10 cm 上下台阶、噪声坡道、地面复用旋转、未知栅格、同格障碍优先、ROS 参数读取、源时间、迟到/无效结果以及真实本机进程通信。
- 1 项已有预期失败是 `test_unknown_policy.py` 的迎面运动压力场景：现有 unknown 静止策略在未确认运动阶段可能碰撞。本次未修改该策略，不能据通过数宣称已解决全部动障安全问题。
- 同一录制最后 100 帧原始点云，修改前后均为 100 个有效观测。核心 p95 从约 10.3 ms 增至约 23.6 ms；新代码的检测数量为 71–213 个，包括新保留的低边界和局部结构块。数量不是目标识别准确率，录制没有逐目标真值。
- 本机 20 Hz 录制点云输入到真实 spawned worker：69 个输入、67 个结果；预热后结果新鲜度合格比例为 100%；worker 处理 p95 约 40.6 ms，源年龄 p95 约 54.2 ms。该项包括点云解析、道路估计、精确聚类、栅格、KF 和进程通信，排除 ROS/DDS 及 Jetson CPU 争用。
- Python 语法解析通过。旧 `docs/validation/test_perception_safety.py` 引用了当前项目已不存在的 `SourcePoseBuffer` 等接口，无法收集测试；旧独立 ROS 替身脚本也不支持当前 TF 定位默认配置。本次使用活动测试和新增的适配器测试验证当前接口，没有宣称旧脚本通过。
- 尚未在车机执行 ROS 构建、DDS 联调或实际道路行驶。

部署包 `campus_perception_fix.zip` 包含三个生产文件，路径从 `src/` 开始；回滚包 `campus_perception_rollback.zip` 包含对应修改前文件。源码 SHA256 见 `delivery_manifest.json`。在车机 ROS 工作空间根目录备份现有文件后解压更新包，再执行：

```bash
colcon build --symlink-install --packages-select rda_dwa_real
source install/setup.bash
ros2 launch car_launch run_rda_dwa.launch.py
```

重启后确认参数和话题，再用 RViz 的 Map 显示 `/rda/drivable_area`，检查道路回波、两侧路沿与未知区域。以下命令只读取数据：

```bash
ros2 param get /lidar_track_node obstacle_height_min
ros2 param get /lidar_track_node dropoff_height
ros2 param get /lidar_track_node ground_reference_z
ros2 topic echo /rda/perception_diag --once
ros2 topic hz /rda/drivable_area
```

关注 `ground_fit_reason`、`ground_reused`、`ground_plane`、`raised_boundary_points`、`dropoff_points`、`exact_distance_tests`、`drivable_grid_summary`、`drivable_published` 和源年龄。车机 CPU 负载下需要重新核查实时耗时，原始点云和道路几何真值应一起记录。
