# 校园小车激光雷达预训练感知选型

检索日期：2026-11-08，Asia/Shanghai。硬件依据用户提供的《小车硬件与雷达信息核对_20261107.md》。附件中的脚本说明和命令没有作为本次操作指令执行。

## 1. 选型结论

**实车第一实施顺序：Autoware CenterPoint base（v4.1，FP16）→ Patchwork++ 与几何占用/聚类 → HARP-NeXt nuScenes 32×480 预训练版 → 多目标跟踪与可行驶栅格。**

上述箭头表示实施顺序。运行时，校准后的点云分别送入检测、语义和几何支路，再融合结果；不要先去除地面再把非地面点替换两个预训练模型所要求的输入。

这是按可下载权重、ROS2 接入、当前算子部署路线和校园任务覆盖做出的工程选型，不是已在用户小车上测出的速度/精度冠军。

- **主检测**：Autoware CenterPoint base，输出人、自行车、汽车、卡车、公交车的带朝向 3D 框。使用发布的 ONNX，不需要训练。首轮用 base，tiny 作为实测算力不足时的备选。
- **道路语义**：HARP-NeXt 的 `harpnext-nuscenes-32x480/ckpt_best.pth`，提供 `driveable_surface`、`sidewalk`、`terrain`、`vegetation` 等逐点标签。作者公开了 AGX Orin 测速和 Jetson 安装说明。
- **类别外障碍**：Patchwork++ 分离地面，非地面点构建占用栅格并聚类，输出 `UNKNOWN` 障碍物。树干、石墩、垃圾桶、低矮杂物等不能仅靠固定类别检测模型覆盖。还需独立检查路沿、高度突变和负障碍。
- **精度升级候选**：DSVT-Pillar nuScenes 预训练版。在公开验证集上精度较高；它的完整 TensorRT 部署、Humble 接入和本机速度需要额外工程验证。

**没有找到已公开验证“RS-Helios-5515 + 用户安装高度 + AGX Orin 64GB + JetPack 6.2 基线 + TensorRT 10.3 + 校园道路”整套组合稳定 10Hz 且达到指定精度的现成包。** 现有权重可以不训练地推理，但点云适配、环境构建和实车验证仍然必要。本次没有连接车机、安装模型或进行实车推理。

## 2. 硬件如何约束选型

| 已确认条件 | 选型含义 |
|---|---|
| AGX Orin 64GB，共享内存，GPU SM87 | 有纯 LiDAR 神经网络部署基础；64GB 不能换算成特定帧率 |
| Ubuntu 22.04、ROS2 Humble、Python 3.10 | 优先 ROS2/C++ 推理节点；研究版 PyTorch 置于隔离环境 |
| CUDA 12.6、cuDNN 9.3、TensorRT 10.3 | 旧 TensorRT 8 示例需审计和迁移；从 ONNX 在本机生成 engine |
| RS-Helios-5515，32线，10Hz，360°，无相机 | 排除需要相机参与推理的融合模型；优先 nuScenes LiDAR-only 权重 |
| 未取得实际 PointCloud2 字段、逐点时间、DIFOP、安装外参 | 不能直接假设原始 ROS 点云符合网络输入，不能假设已去畸变 |
| 采集时系统绝对时间未同步 | 先核实雷达、ROS、里程计时间域，避免跨时钟融合和校时跳变 |

RoboSense 官方说明 Helios 32 的垂直视场为 70°，其中地平线以下为 55°，对应 5515 约 −55°～+15°。[RoboSense 产品说明](https://www.robosense.ai/en/IncrementalComponents/Helios)

nuScenes 使用 32 线、20Hz LiDAR，垂直视场 −30°～+10°。[nuScenes 论文](https://arxiv.org/abs/1903.11027)

因此，“32 线”只是一个有利匹配条件。射线分布、视场、强度响应、安装高度和采样频率仍不同。若实际安装很低，贴近地面看到的目标形态也会与车顶雷达数据不同。附件中的 0.45m 仅是已有配置值，本次不作为实测高度。

### 为什么先用 Autoware base

Autoware base 提供已经导出的 ONNX，不必在车机上完整搭建训练版 MMDetection3D/spconv 再导出。节点明确接收 PointCloud2 并输出 DetectedObjects，且当前 CUDA 构建包含 SM87。它采用 PointPillars 风格编码和 CenterPoint 检测头，避免把 NVIDIA VoxelNet 的二进制稀疏骨干依赖作为第一实施步骤。

base 与 tiny 分别固定了自己的参数/网络。tiny 的较低输出分辨率存在速度与精度取舍；校园行人与自行车重要，首轮先评估 base。当前公开证据不能证明 base 在本校一定比 DSVT 精度更高。

`short_range` 专用近场权重虽已公开，但训练资料和比较指标尚不完整，不能仅因名称符合校园近场就判定最好。相同理由下不默认同时启动多个检测器。

## 4. 可行驶区域：选 HARP-NeXt 的 nuScenes 版本

HARP-NeXt 是 IROS2025 的纯 LiDAR 语义分割模型；其范围图由点云生成，推理不需要相机。

| 项目 | 已核实内容 |
|---|---|
| 具体 checkpoint | `harpnext-nuscenes-32x480/ckpt_best.pth` |
| 下载位置 | [Hugging Face 权重](https://huggingface.co/samir-abh/HARP-NeXt/tree/main/harpnext-nuscenes-32x480) |
| 核实方式 | 模型 API 列出文件；HEAD 返回 HTTP200，checkpoint 大小 64,865,210 字节；未下载或执行 checkpoint |
| 标签 | 16 类，包括 driveable_surface、sidewalk、terrain、manmade、vegetation 和多类交通目标 |
| nuScenes val 精度 | 整体 mIoU **77.1%**；driveable_surface 类 IoU **97.7%** |
| AGX Orin 速度 | 作者报告总运行时间约 **71ms / 帧，即 14.1 FPS**，不包含用户完整 ROS/规划系统的验证 |
| 推理部署 | 官方发布 PyTorch/Jetson 安装说明；Jetson 测试基线是 JetPack6.0，不是本车6.2；仍需匹配 ARM64 PyTorch 与 torch-scatter |

来源：[官方仓库](https://github.com/SamirAbouHaidar/HARP-NeXt)、[论文及类别指标](https://arxiv.org/abs/2510.06876)、[官方 nuScenes 配置](https://github.com/SamirAbouHaidar/HARP-NeXt/blob/main/configs/net/harpnext-nuscenes.yaml)。

优先 nuScenes 权重，因为它的 32 线数据来源与本车较接近。SemanticKITTI 64×512 版在作者 AGX Orin 比较中约 8.3FPS，传感器采样也更不匹配。

HARP-NeXt 输出道路语义后，还要构建车辆可通行区域：

1. 只把新鲜、足够置信且实际观测到的道路语义格子作为候选。
2. 与地面几何约束相交：坡度、局部粗糙度、高度台阶、路沿和可用净空。
3. 扣除非地面占用、检测框、跟踪预测范围和车体所需安全间距。
4. 若已有校园道路地图，再与允许通行道路边界相交。
5. 保留 `FREE / OCCUPIED / UNKNOWN`，遮挡和未观测区域不自动变成可行驶。

driveable_surface 的高 IoU 是数据集语义结果，不表示该处实时无障碍或符合小车尺寸、底盘通过能力与校园通行规则。Patchwork++ 的 ground 标签也不能单独把草地、台阶或人行道变成可行驶道路。

## 5. 具体权重与部署边界

### 主检测固定版本

使用 [AutowareFoundation/lidar_centerpoint 的 v4.1](https://huggingface.co/AutowareFoundation/lidar_centerpoint/tree/v4.1/base)，包含：

```text
base/pts_voxel_encoder.onnx
base/pts_backbone_neck_head.onnx
base/ml_package.param.yaml
base/detection_class_remapper.param.yaml
```

v4.1 模型仓库 revision：`494c8171def40bd36cc2feb323e0a5acbfab132b`。本次对两个 ONNX 的 HEAD 均为 HTTP200；分别为 7,429 和 20,140,082 字节。模型文件的可访问性已经核对，网络数值与实车效果尚未验证。

同时固定与 v4.1 manifest 匹配的节点源码和依赖，按 Ubuntu22.04/Humble/ARM64 编译。不能把新模型包直接塞入不识别其 manifest 的旧节点。当前节点使用 TensorRT `enqueueV3`，说明有现代 API 路线，但完整 Humble 与 TensorRT10.3 编译运行仍需要本机检查。

ONNX 转 TensorRT engine 是部署构建，不是训练。engine 应在目标 Orin、目标 TensorRT10.3 环境生成；不要复用 RTX/Drive/旧 TensorRT 生成的 engine。

### 输入适配必须完成的工作

- 核实 PointCloud2 的 `fields / offsets / datatype / point_step`。当前 Autoware CenterPoint 节点期待 PointXYZIRC 布局，含 xyz、uint8 intensity、return_type、channel；字段名相似不保证内存布局相同。HARP-NeXt 的四通道网络输入是 xyz+intensity。
- 使用实测外参、DIFOP 标定和坐标轴约定；核对 z 原点、box 中心/底面约定、长宽顺序和 yaw 方向。
- intensity 按各模型原始预处理保持一致，不能统一假设“全部除以255”；ring/channel 不能代替模型要求的时间特征。
- 核实逐点时间、帧时间和去畸变；多帧累积使用可靠里程计做自车运动补偿，动态目标仍可能出现拖影。
- **HARP 投影要专门检查视场外点。** 官方 nuScenes 配置为 H32/W480/FOV−30°～+10°，本车全视场不同。不能把全部 Helios 点盲目夹到范围图边缘，也不能只改 FOV 后承诺原始精度。可将训练视场重合区域作为第一适配基线，在校园回放中对比；全视场点仍由几何占用支路处理。裁剪会造成输入变化，准确性必须重新评价。
- 保持 checkpoint 对应的 voxel、网络 shape、输出 stride 和输入特征。缩小网络栅格或改变网络通道不是可任意进行的免训练提速。应用 ROI 可以先用于下游发布/几何支路；缩小输入范围是否加速取决于网络与实际算子。
- NVIDIA CUDA-CenterPoint 所用官方配置为 10 sweeps、5特征；不能当成任意单帧 XYZI 检测器。nuScenes20Hz 与本车10Hz 的历史时间跨度不同。若评估此路线，应同时检查历史时间窗、点密度和动态拖影，不机械累计10帧，也不把不同累积设置的结果视为论文指标。

### 障碍物信息的分工

| 信息 | 产生方式 |
|---|---|
| 类别、置信分数、中心 xyz、长宽高、yaw | 3D 检测网络与后处理；当前 base 为5类 |
| UNKNOWN 障碍及轮廓/几何框 | 非地面点、占用、聚类与形状估计 |
| 最近距离 | 原始/聚类点到车体轮廓的距离，不能只用检测框中心距离 |
| track_id、速度 vx/vy、静止/运动状态 | 多帧跟踪与自车运动补偿；base manifest 为 `has_twist:false`，不能默认它直接输出可靠速度 |
| 测量时间、数据年龄、观测/预测状态 | ROS 输入输出和跟踪状态管理 |
| 预测占用、碰撞时间估计 | 跟踪/运动预测与规划层；不属于单帧检测网络直接输出 |

## 6. 实时运行建议与验收

**首轮目标建议：障碍/占用10Hz，道路语义5Hz，随后根据并行实测决定是否把语义提升到10Hz。** 这是工程初始预算，不是已测性能。

即使采用公开的 NVIDIA Orin CenterPoint 约42ms样例与 HARP约71ms估计，两者串行约113ms，只有约8.8FPS。两个模型分别超过10FPS并不证明同时能10Hz；GPU并发也不会自动消除资源竞争。该估计跨实现/平台，只用于提醒预算，不能预测 Autoware base 的实际速度。

道路语义较低频时，实时几何占用仍处理最新点云；语义栅格需要自车位姿对齐、数据年龄检查和失效处理。检测缓存采用最新帧策略，避免低帧率推理堆积成高延迟。

无需重新训练的验收流程：

1. 从本车采集校门、人流路段、停车区、窄路、坡道、路沿等 rosbag；同时记录可靠里程计和时间信息。
2. 使用同一批回放对 base、必要时 tiny/DSVT/TransFusion 比较人、自行车和机动车。近场0～30m可作为第一评估范围，最终范围取决于车速与制动距离。
3. 给回放标注一小批真值，统计分类别/分距离召回、误检、框误差、跟踪稳定性和可行驶区域误放行。标注用于评估，不需要参与训练。
4. 在车机定位、规划同时运行时测推理及 ROS 全链路 P50/P95/P99、输出年龄、实际新帧率、温度与丢帧。算法处理预算100ms与扫描本身的时间跨度分开记录。
5. 检查行人横穿、多人相邻、自行车、石墩、树干、锥桶、低物体、台阶和遮挡区；特别关注“没有检测框但实际被占用”的情况。

若预训练模型在校园数据上未达到所需召回率，即使运行速度合格，也不能通过参数调整宣称已达到实车精度。在禁止训练的约束下，可更换预训练权重、比较候选并加强几何支路，但不存在保证所有跨域问题均可免训练解决的依据。

Patchwork++ 官方仓库包含 C++ 和 ROS2/Humble 示例，不需要模型训练；其作用是地面分离。[Patchwork++](https://github.com/url-kaist/patchwork-plusplus)

## 7. 检索覆盖与证据边界

本次使用公开论文、作者仓库、NVIDIA 与 Autoware 官方代码/模型卡和 Hugging Face 文件列表。技能默认的 `papers/`、`literature/` 目录没有贡献本地 PDF；没有读取附件外的生产算法作为部署授权。
